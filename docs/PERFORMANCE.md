# DiskAnalyzer 性能验证（Step 5）

## 测试环境与方法

- 构建：.NET 8 Release；
- 文件系统：本机 Windows 文件系统；
- 文件内容：0 字节，目的是隔离目录枚举和元数据读取开销；
- 每组工作线程配置重复运行 3 次；
- 数据已进入文件系统缓存，因此结果代表“热缓存元数据扫描”，不代表冷启动 HDD；
- 基准工具：`tools/DiskAnalyzer.Benchmarks`。

运行方式：

```powershell
dotnet run --project tools\DiskAnalyzer.Benchmarks `
  --configuration Release -- <目录> <工作线程数>
```

## 场景 A：20,000 文件，50 个子目录

| 目录工作线程 | 三次吞吐量（文件/秒） | 中位数 |
|---:|---:|---:|
| 1 | 623,904 / 614,105 / 583,752 | 614,105 |
| 2 | 592,044 / 600,393 / 594,391 | 594,391 |
| 4 | 580,666 / 596,047 / 569,178 | 580,666 |

文件集中、元数据已缓存时，并发调度没有收益，单工作线程最快。

## 场景 B：20,000 文件，2,000 个子目录

| 目录工作线程 | 三次吞吐量（文件/秒） | 中位数 |
|---:|---:|---:|
| 1 | 137,771 / 147,245 / 151,476 | 147,245 |
| 2 | 149,087 / 152,538 / 150,060 | 150,060 |
| 4 | 149,616 / 154,561 / 153,386 | 153,386 |

目录密集场景中，小规模并发带来约 2%～4% 的中位数提升；4 个工作线程比单线程约快 4%。

## 内存测量

- 20,000 文件、2,000 目录；
- 2 个目录工作线程；
- 保留所有 `FileItem`，模拟 UI 列表；
- 托管总分配约 10.3 MB；
- 扫描结束后保留托管内存约 5.6 MB。

此数据使用很短的合成路径。真实磁盘路径更长，因此不能直接按比例推算实际峰值内存。

## 已实施优化

- 目录扫描采用可配置的有界工作线程，默认 2 个，硬上限 16；
- 文件结果仍通过容量为 4096 的有界通道传输；
- `FileItem` 只长期保存完整路径、大小和时间；
- 文件名和扩展名从完整路径按需计算并缓存，避免所有文件立即保存重复字符串；
- UI 每 500 条或约 200 ms 提交一次，兼顾吞吐量和可见反馈；
- 扫描进度节流到约 150 ms；
- 扫描过程中不进行全量排序；
- 每次向调用方产出结果前检查取消令牌，避免取消后继续排出通道缓冲。

## 默认值决策

默认使用 2 个目录工作线程：

- 比 4 个线程更保守，降低 HDD 随机访问和线程调度成本；
- 在目录密集场景比单线程略快；
- 在文件集中场景只产生小幅损失；
- 可通过 `FileScannerOptions.DirectoryWorkerCount` 调整，方便后续针对 HDD、SATA SSD 和 NVMe 实测。
